## Scope rules

1. The primary accepted exceptions are P4-2, P4-5, P4-6, and the Windows Npcap
   raw-SYN limitation.
2. P4-1, P4-3, and P4-4 may be removed from this acceptance only if a signed
   release run produces published OIDC provenance/SBOM attestations and the
   verification is recorded before approval. Until then, they remain accepted
   risks.
3. Removing channels from the announcement does not close P4-2. It only avoids
   claiming ownership that has not been confirmed.
4. This acceptance does not close P4-1 through P4-6 and must never be described
   as P4 closure.

## Accepted risks

| ID | Risk | Impact if accepted | Compensating control | Residual risk |
|---|---|---|---|---|
| P4-1 | No approved production signing identity or independently verified key custody | Users cannot verify an independently approved production signature; authenticity depends on published checksums, the repository, and any locally verified release signature | Use a dedicated release key; publish the public key and full fingerprint; record the custody limitation; sign checksums; verify from a clean host; do not claim independent custody approval | Artifact origin remains only as trustworthy as the distribution channel and signer custody |
| P4-2 | Registry ownership, 2FA/recovery, and clean-install evidence are absent | No package channel is authorized; an unofficial channel could confuse users | Publish only through channels with confirmed ownership; remove Chocolatey, AUR, Docker Hub, and any other unowned channel from the announcement; keep packaging metadata local until approved | Users may install from an unofficial or unverified source |
| P4-3 | No clean-runner release evidence | Reproducibility and runner isolation are unproven | Run the signed workflow from a clean checkout with `--locked`; retain logs and hashes; verify from a separate clean Debian host; label the result as workflow evidence, not P4 closure | A compromised or undeclared dependency could affect artifacts |
| P4-4 | No published build-provenance or SBOM attestations | Provenance and SBOM association cannot be independently verified from a published release | Generate and checksum the CycloneDX SBOM; use the tag-triggered OIDC attestation workflow; publish and verify the attestations; do not claim them if absent | SBOM and provenance trust remain unproven |
| P4-5 | No independent OT/ICS security assessment | OT/ICS-specific security claims are not independently validated | Do not market the release as OT/ICS-assessed; preserve the assessment as a blocking requirement; state the limitation in the release notes | Unknown OT/ICS-specific weaknesses may remain |
| P4-6 | No named reviewer sign-off or completed formal review | The release has not received formal P4 approval | Keep the P4 checklist open; record this risk acceptance as the governing exception; require named approval before publication | Governance and documentation defects may remain |
| Platform | Windows Npcap raw-SYN runtime is unverified | Windows raw features may fail or behave differently | Verify on Windows if possible; otherwise publish an explicit waiver naming the affected features and limitations | Windows raw-SYN users may encounter unsupported behavior |
| Platform | Full-range raw SYN parity on PingPong is unresolved | Full-range completeness is not established for that environment | Document the 1/15 full-range result and the 15/15 cooldown result; do not claim parity | Users may overestimate full-range reliability in similar environments |

## Mandatory publication labeling

The following wording must appear in the release title, release notes, and the
README release-status section:

> **Risk-accepted release. P4 is not closed. Not independently assessed for
> OT/ICS environments.**

The release notes must also state:

- Windows Npcap raw-SYN is unverified or covered by the recorded waiver.
- Full-range PingPong parity is not established.
- No registry ownership is claimed for Chocolatey, AUR, Docker Hub, or any other
  unconfirmed channel.
- The release is published only through channels with confirmed ownership.
- No production-approved key custody or independent OT/ICS assessment is claimed
  unless the corresponding evidence is published and linked.

## Conditions

1. The accountable owner must approve this document with a name, role, date,
   expiry, and signature or verifiable approval reference.
2. The GitHub token exposed during this work must be revoked immediately and
   replaced with a least-privilege token. The exposed token must not be used for
   any push, workflow, or secret operation.
3. A dedicated release key must be generated, its public key and full fingerprint
   published, and its private key added to GitHub Actions secrets through the
   owner-controlled UI. Local private key material and passphrases must be
   removed after the secrets upload and successful verification.
4. The signed workflow must run from a clean checkout, produce the SBOM and
   OIDC attestations, and be verified from a clean Debian host before P4-1,
   P4-3, or P4-4 is described as satisfied.
5. Do not tag, push, publish, or promote `1.0.0` until this approval is signed,
   the release preflight passes from a clean tree, and the owner gives explicit
   publication authorization.
6. Remove unowned channels from the announcement instead of claiming them.
7. This acceptance expires on the recorded expiry date. It does not renew
   automatically.
8. Any artifact rebuild, version change, source change, or key change invalidates
   this acceptance and requires a new approval.
